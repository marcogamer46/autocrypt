- Date: 2026-11-08
- Platform: Windows 11, Python 3.12.16
- Scope: honest, reproducible comparison on **real, held-out CTF challenges** (challenges not written by the autocrypt author), plus autocrypt's own fixtures as sanity checks.

## Narrative

**How to read this.** The challenge set deliberately mixes (a) real, public CTF challenges that the autocrypt author did not write — PicoCTF 2021/2022/2023, CSAW Red 2020 — and (b) autocrypt's own fixtures, included only as sanity checks. The honest yardstick is (a).

**Where autocrypt wins.**
- **Small-exponent RSA** is a genuine strength: it solved `minirsa` (e=3) and `Mini_RSA` (e=3 with the `c+i·n` twist). RsaCtfTool also solved plain e=3, but its `cube_root` attack *failed* on Mini_RSA because it does not iterate the multiplier `i` — autocrypt did. This is a real win.
- **Classical substitution** is solved cleanly: all three PicoCTF 2023 `substitution*` challenges recovered the correct flag (one with the known J/Q letter ambiguity). These are exactly the challenges Ciphey would normally be the reference for, but Ciphey could not be installed, so no head-to-head.
- It also handled the easy Caesar (`rotation`) and its own fixtures.

**Where autocrypt loses.**
- **Sum-O-Primes** (picoCTF 2022): given `x = p+q`, autocrypt produced only confidence-0.06 junk. RsaCtfTool recovered the flag via FactorDB. (Fair caveat: RsaCtfTool did it by factoring n, not by using `x`; still, it got the right answer and autocrypt did not.)
- **rail-fence** (picoCTF 2022): a simple transposition that autocrypt missed entirely ("No weakness found").
- **Very_Smooth**: despite the repo README claiming a p−1 solve, my reproducible runs (25 s and 120 s) recovered no flag — only low-confidence substitution junk. RsaCtfTool also failed here (default timeout; targeted `pollard_p_1` gave nothing). I record this honestly rather than trusting the README claim.
- **`e5_270rsa_rev`** and **`multiprime`**: autocrypt timed out on both; RsaCtfTool got raw (reversed) bytes on the former and simply does not support multi-prime on the latter.

**Where the comparison is incomplete (honest caveats).**
- **Ciphey could not be installed** on Python 3.12 (its `cipheycore` wheel is capped at CPython 3.9, no sdist, and there is no older interpreter or Rust toolchain on this machine). So the "Ciphey" column is entirely N/A. I did not fabricate results. If you can provide a Python ≤3.9 environment, running `pip install ciphey` there and re-running the substitution rail-fence/rotation files would fill the biggest gap.
- **RsaCtfTool's FactorDB-dependent results** (`sumoprimes`, `e5_270rsa`) require Internet. Offline, those two would likely fail too.
- **Flag verification** relies on public writeup flags; for `multiprime` and `Very_Smooth` no public flag was reproduced, so those rows are "measured behavior" rather than "solved/not-solved against a flag".

**Bottom line.** autocrypt is competitive — sometimes better — on the "classical" side it targets (small-e RSA, substitution, Caesar). It is **not** a general CTF solver: it misses simple transpositions (rail-fence), the p+q trick (Sum-O-Primes), and its README's p−1 success did not reproduce in my runs. RsaCtfTool remains the stronger general RSA tool (FactorDB, multi-attack), but it is RSA-only and even it misses Mini_RSA's e=3 twist that autocrypt catches. The most honest summary: *autocrypt is a fast, effective specialist for the cipher families it was built for, but it should not be marketed as a drop-in replacement for a general CTF crypto toolkit.*

## Reproducing this benchmark

```bash
# autocrypt
.venv/Scripts/python.exe -m autocrypt.cli real_challenges/<name>/<file> --timeout 25 --top 5

# RsaCtfTool (installed in .venv_bench)
.venv_bench/Scripts/RsaCtfTool.exe -n <N> -e <E> --decrypt <C> --attack cube_root --timeout 60

# Ciphey: not installable here (see environment section)
```
